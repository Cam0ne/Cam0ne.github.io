模型微调

发表于2026-08-05|更新于2026-08-07|AI开发

基础概念

模型微调（Fine-tuning）是指在一个已经完成预训练的基础模型上，使用特定任务的数据继续训练，让模型更稳定地适应目标场景、输出格式和业务规则。相比从零训练模型，微调通常需要更少的数据、更低的算力和更短的训练周期。

微调并不是让模型“重新学会所有知识”，而是让模型在已有通用能力之上，进一步学习：

  • 应该如何理解输入
  • 应该按照什么格式输出
  • 哪些答案是符合任务要求的
  • 哪些回答风格、边界和约束需要保持一致

微调目标

微调前必须先明确目标，否则后续数据构造、训练配置和评估指标都会失焦。

一个通用的微调目标可以写成：

给定一段输入文本，模型需要根据任务规则生成结构化结果，并保持输出稳定、可解析、可评估。

常见目标包括：

  • 分类：判断输入属于哪个类别
  • 抽取：从输入中提取实体、字段或关键信息
  • 生成：按照固定风格生成摘要、回复或报告
  • 问答：根据上下文回答问题
  • 工具调用：输出符合 Schema 的参数

如果目标输出需要进入程序处理，建议优先使用 JSON、YAML 或固定字段格式，而不是自然语言长段落。

示例输出结构：

{
  "label": "category_a",
  "confidence": 0.91,
  "reason": "输入中包含与 category_a 匹配的关键特征"
}

方案选择

微调之前先判断是否真的需要微调。很多问题可以通过提示词、RAG 或规则系统解决。

方案 适用场景 特点
Prompt 优化 任务简单、规则少、数据变化快 成本低，迭代快
RAG 需要引用外部知识库、事实经常更新 不改变模型参数
SFT 微调 有稳定输入输出样本，希望模型学会固定任务 输出更稳定
LoRA / QLoRA 算力有限，希望低成本训练 只训练少量适配参数
全参数微调 数据量大、算力充足、任务差异明显 成本高，风险也高

一般实践顺序：

  1. 先用 Prompt 验证任务是否可行
  2. 再构造少量样本测试输出稳定性
  3. 如果输出格式、任务理解或风格仍不稳定，再考虑 SFT
  4. 如果显存有限，优先选择 LoRA 或 QLoRA

数据准备

数据质量通常比训练技巧更重要。微调数据不是越多越好，而是越清晰、一致、覆盖关键场景越好。

定义样本格式

建议把每条样本整理成统一结构：

{
  "id": "sample_000001",
  "input": "这里放模型需要处理的输入内容",
  "output": {
    "label": "category_a",
    "confidence": 0.91,
    "reason": "判断依据"
  },
  "meta": {
    "source": "optional",
    "version": "v1"
  }
}

其中：

  • input 是模型看到的任务输入
  • output 是期望模型学习的标准答案
  • meta 只用于数据管理，不一定进入训练

清洗与归一化

清洗目标是去掉噪声、统一格式、降低样本之间的无意义差异。

必要步骤：

  • 去除空样本、乱码样本、重复样本
  • 统一编码、大小写、时间格式、字段名称
  • 删除无关字段，例如 ID、随机 token、临时路径
  • 对超长输入做截断或摘要，避免超过模型上下文长度
  • 对敏感信息做脱敏处理

伪代码：

def clean_sample(raw):
    text = normalize_encoding(raw["input"])
    text = remove_noise(text)
    text = mask_sensitive_info(text)
    text = truncate_by_tokens(text, max_tokens=2048)

    if not text.strip():
        return None

    return {
        "id": raw["id"],
        "input": text,
        "output": normalize_output(raw["output"])
    }

去重

重复样本会让模型过度记忆某些模式，导致评估分数虚高。

伪代码：

seen = set()
deduped = []

for sample in samples:
    fingerprint = hash_text(sample["input"])
    if fingerprint in seen:
        continue

    seen.add(fingerprint)
    deduped.append(sample)

类别平衡

如果某些类别样本过多，模型容易学成“永远预测多数类”。因此需要检查标签分布。

from collections import Counter

label_count = Counter(sample["output"]["label"] for sample in samples)
print(label_count)

常见处理方式：

  • 多数类下采样
  • 少数类过采样
  • 为关键类别补充高质量样本
  • 将模糊样本单独标记，避免污染训练集

构造 SFT 数据集

SFT（Supervised Fine-Tuning）需要把样本组织成“指令 → 回答”的形式。对于 Chat 模型，通常使用 messages 格式。

示例：

{
  "messages": [
    {
      "role": "system",
      "content": "你是一个任务助手。请严格按照 JSON 格式输出，不要输出多余文本。"
    },
    {
      "role": "user",
      "content": "请处理以下输入：\n这里是待处理文本"
    },
    {
      "role": "assistant",
      "content": "{\"label\":\"category_a\",\"confidence\":0.91,\"reason\":\"判断依据\"}"
    }
  ]
}

构造时要注意：

  • system prompt 保持稳定，不要每条样本随意变化
  • assistant 输出必须是可解析的标准答案
  • 输出字段名称、枚举值、空值规则要固定
  • 不要把测试集样本混入训练集

伪代码：

def build_chat_sample(sample):
    system = "你是一个任务助手。请严格输出 JSON。"
    user = f"请处理以下输入：\n{sample['input']}"
    assistant = json.dumps(sample["output"], ensure_ascii=False)

    return {
        "messages": [
            {"role": "system", "content": system},
            {"role": "user", "content": user},
            {"role": "assistant", "content": assistant}
        ]
    }

数据集划分

数据集至少应划分为：

数据集 用途 是否参与训练
训练集 更新模型权重 是
验证集 训练过程中观察泛化能力 否
测试集 训练完成后做最终评估 否

推荐按标签分层划分，避免某些类别只出现在训练集或测试集里。

伪代码：

train, valid, test = stratified_split(
    samples,
    label_key=lambda x: x["output"]["label"],
    ratios=(0.8, 0.1, 0.1),
    seed=42
)

验证集的意义：

  • 观察模型是否过拟合
  • 调整学习率、epoch、batch size 等参数
  • 决定是否提前停止训练

测试集的意义：

  • 只在最终评估时使用
  • 衡量模型在未见样本上的真实表现
  • 避免训练过程反复调参导致“测试集泄漏”

微调训练

如果使用 LoRA 或 QLoRA，训练时通常冻结基础模型，只训练少量适配参数。这样可以显著降低显存和训练成本。

训练配置

常见配置项：

配置 说明
base_model 基础模型路径或名称
max_seq_length 最大上下文长度
learning_rate 学习率
epochs 训练轮次
batch_size 单卡批量大小
gradient_accumulation_steps 梯度累积步数
lora_rank LoRA 低秩矩阵大小
lora_alpha LoRA 缩放系数
eval_steps 每隔多少步评估一次

示例命令：

python train_lora.py \
  --base_model path/to/base-model \
  --train_file data/train.jsonl \
  --valid_file data/valid.jsonl \
  --output_dir output/task-lora \
  --max_seq_length 2048 \
  --learning_rate 2e-4 \
  --epochs 3

训练主流程伪代码

model = load_base_model("path/to/base-model", quantization="4bit")
tokenizer = load_tokenizer("path/to/base-model")

model = add_lora_adapter(
    model,
    rank=16,
    alpha=32,
    dropout=0.05,
    target_modules=["q_proj", "v_proj"]
)

train_dataset = load_jsonl("data/train.jsonl")
valid_dataset = load_jsonl("data/valid.jsonl")

trainer = Trainer(
    model=model,
    tokenizer=tokenizer,
    train_dataset=train_dataset,
    eval_dataset=valid_dataset,
    learning_rate=2e-4,
    epochs=3,
    batch_size=2,
    gradient_accumulation_steps=8,
    eval_steps=500,
    save_steps=500
)

trainer.train()
trainer.save_model("output/task-lora")

训练过程观察

训练时重点观察：

  • train_loss 是否稳定下降
  • eval_loss 是否同步下降
  • eval_loss 是否在后期上升
  • 输出 JSON 是否仍然合法
  • 模型是否开始生成多余解释文本

如果出现 train_loss 下降但 eval_loss 上升，通常说明过拟合。可以考虑：

  • 减少 epoch
  • 降低学习率
  • 增加 dropout
  • 增加高质量样本
  • 提前停止训练

模型评估

微调完成后，不能只看 loss，还要用任务指标评估模型是否真的可用。

结构化输出检查

如果要求模型输出 JSON，首先检查格式合规率。

伪代码：

def is_valid_json(text):
    try:
        obj = json.loads(text)
        return required_keys_exist(obj)
    except Exception:
        return False

valid_count = 0

for item in test_set:
    pred = model_generate(item["input"])
    if is_valid_json(pred):
        valid_count += 1

json_valid_rate = valid_count / len(test_set)

分类指标

如果任务包含分类字段，可以计算准确率、精确率、召回率和 F1。

pred_labels = []
gold_labels = []

for item in test_set:
    pred = parse_json(model_generate(item["input"]))
    pred_labels.append(pred["label"])
    gold_labels.append(item["output"]["label"])

report = classification_report(gold_labels, pred_labels)
print(report)

常见指标含义：

指标 含义
Accuracy 总体预测正确比例
Precision 被预测为某类的样本中，有多少是真的
Recall 某类真实样本中，有多少被找出来
F1 Precision 和 Recall 的综合指标
Macro-F1 各类别 F1 的平均值，适合类别不均衡场景

人工抽检

自动指标只能说明一部分问题。对于高风险任务，还需要人工抽检。

抽检重点：

  • 模型是否遵守输出格式
  • 判断理由是否自洽
  • 边界样本是否稳定
  • 少数类是否被忽略
  • 是否出现幻觉、编造依据或过度自信

合并与部署

LoRA 微调后通常会得到一个 adapter，而不是完整模型。部署时有两种方式：

方式 说明
基础模型 + adapter 灵活，便于切换多个任务
合并模型 加载更简单，部署链路更短

合并伪代码：

base_model = load_base_model("path/to/base-model")
adapter = load_lora_adapter(base_model, "output/task-lora")

merged_model = merge_adapter(base_model, adapter)
merged_model.save_pretrained("output/task-merged")

部署前需要验证：

  • 模型能正常加载
  • 推理结果与合并前基本一致
  • 输出格式稳定
  • 显存占用符合预期
  • 单条请求耗时满足业务要求

标准流程总结

步骤 阶段 主要目标 关键内容 输出结果
1 明确任务目标和输出格式 定义模型需要解决的问题 明确任务类型（分类、问答、生成、抽取等）；定义输入格式和输出 Schema 任务定义文档、输出规范
2 判断是否真的需要微调 评估微调必要性 对比 Prompt Engineering、RAG、Agent 是否可以满足需求；评估数据量、成本和收益 微调决策方案
3 收集并清洗样本 构建高质量训练数据 收集业务数据；去重、去噪、纠错；删除无效和敏感数据 原始训练样本集
4 统一标签、字段和输出 Schema 保证数据一致性 统一标签体系；规范字段名称；定义 JSON、文本等输出结构 标准化数据 Schema
5 构造 SFT messages 数据集 转换为监督微调格式 构造 system、user、assistant 三角色数据；生成符合模型训练格式的数据 SFT Dataset（JSONL）
6 分层划分训练集、验证集、测试集 保证评估可靠 按业务场景、难度、类别进行划分；常见比例：Train 70%、Valid 15%、Test 15% Train / Validation / Test 数据集
7 使用 LoRA 或 QLoRA 进行训练 高效调整模型能力 冻结基础模型参数，仅训练 Adapter；降低显存占用和训练成本 微调后的 Adapter 权重
8 观察 train_loss 和 eval_loss 判断训练效果 监控训练损失和验证损失变化；判断收敛、欠拟合、过拟合 Loss 曲线分析
9 在测试集上计算任务指标 客观评估模型能力 根据任务计算 Accuracy、Precision、Recall、F1、BLEU、ROUGE 等指标 模型评测报告
10 人工抽检关键样本 验证实际效果 检查高风险场景、边界案例、错误回答、格式稳定性 人工评测结果
11 合并 Adapter 或部署基础模型 + Adapter 上线模型服务 选择 Merge 权重部署，或运行时加载 Adapter；配置推理服务 可部署模型
12 持续收集失败样本并迭代 建立持续优化闭环 收集线上错误案例；分析失败原因；补充数据重新训练 新一轮训练数据和模型版本

部署目标 本地大模型要真正接入业务，不能只停留在命令行对话 Demo。更常见的形态是把模型部署成一个稳定的 HTTP 服务，让脚本、RAG 系统、Agent 框架、内部平台都能通过统一接口调用。 vLLM 的定位正好在这里：它提供高性能推理引擎，并且内置 OpenAI 兼容接口。只要服务启动成功，上层应用可以像调用 OpenAI API 一样调用本地模型。 部署前先确认三件事 部署 vLLM 之前，不建议直接复制启动命令。先确认三个边界，可以少踩很多坑。 显存是否够 模型越大，显存压力越高。除了模型权重本身，还要考虑 KV Cache、上下文长度、并发请求和 batch 调度带来的额外占用。 可以先用一个保守原则： 单卡显存紧张时，优先选小模型或量化模型 上下文长度不确定时，不要一开始就拉满 --max-model-len 并发需求不明确时，先单并发跑通，再逐步压测 多卡部署时，再考虑 --tensor-parallel-size 接口给谁用 如果只是本机测试，用 127.0.0.1 监听即可。如果要给局域网或业务系统调用，再开放到 0.0.0.0，并配合防火墙、反向代理...
