vLLM 本地推理服务部署

发表于2026-08-06|更新于2026-08-06|AI开发

部署目标

本地大模型要真正接入业务，不能只停留在命令行对话 Demo。更常见的形态是把模型部署成一个稳定的 HTTP 服务，让脚本、RAG 系统、Agent 框架、内部平台都能通过统一接口调用。

vLLM 的定位正好在这里：它提供高性能推理引擎，并且内置 OpenAI 兼容接口。只要服务启动成功，上层应用可以像调用 OpenAI API 一样调用本地模型。

部署前先确认三件事

部署 vLLM 之前，不建议直接复制启动命令。先确认三个边界，可以少踩很多坑。

显存是否够

模型越大，显存压力越高。除了模型权重本身，还要考虑 KV Cache、上下文长度、并发请求和 batch 调度带来的额外占用。

可以先用一个保守原则：

  • 单卡显存紧张时，优先选小模型或量化模型
  • 上下文长度不确定时，不要一开始就拉满 --max-model-len
  • 并发需求不明确时，先单并发跑通，再逐步压测
  • 多卡部署时，再考虑 --tensor-parallel-size

接口给谁用

如果只是本机测试，用 127.0.0.1 监听即可。如果要给局域网或业务系统调用，再开放到 0.0.0.0，并配合防火墙、反向代理或 API Key 控制访问。

模型服务通常不应该裸露在公网。

模型目录怎么管理

建议把运行环境、模型文件、日志文件分开放：

~/ai-runtime/
├── vllm_env/
├── models/
│   └── <model-dir>/
└── logs/
    └── vllm.log

后续升级模型、回滚版本、定位日志都会更清楚。

检查 GPU 环境

先确认系统能识别 NVIDIA GPU：

nvidia-smi

重点关注：

  • Driver Version：驱动是否正常
  • CUDA Version：驱动支持的 CUDA 版本
  • Memory-Usage：空闲显存是否足够
  • Processes：是否已有其他进程占用 GPU

如果这一步失败，优先修复驱动或 CUDA 环境。不要急着安装 Python 依赖，否则后面大概率会遇到 torch.cuda.is_available() 为 False 或 CUDA 初始化失败。

创建独立 Python 环境

建议为 vLLM 单独创建虚拟环境：

mkdir -p ~/ai-runtime
cd ~/ai-runtime

python3 -m venv vllm_env
source vllm_env/bin/activate
python -m pip install -U pip

确认当前 Python 指向虚拟环境：

which python
python --version

如果机器上同时存在 Conda、系统 Python、多个项目虚拟环境，这一步很关键。很多依赖问题本质上是装在了错误的 Python 环境里。

安装 PyTorch 和 vLLM

根据机器 CUDA 环境安装对应版本的 PyTorch。下面是 CUDA 12.1 的示例：

pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu121

安装 vLLM：

pip install vllm

Ubuntu 环境通常还需要基础编译依赖：

sudo apt update
sudo apt install -y python3-dev build-essential

安装完成后验证：

python -c "import torch; print(torch.cuda.is_available()); print(torch.version.cuda)"
python -c "import vllm; print(vllm.__version__)"

期望结果：

  • torch.cuda.is_available() 输出 True
  • torch.version.cuda 有 CUDA 版本
  • vllm.__version__ 能正常打印

如果 PyTorch 无法识别 GPU，先检查 PyTorch 安装源和 CUDA 版本，不要继续启动 vLLM。

下载模型到本地

如果模型在 Hugging Face，可以安装命令行工具：

pip install -U "huggingface_hub[cli]"

按需设置镜像：

export HF_ENDPOINT=<huggingface-mirror-url>

下载模型：

huggingface-cli download --resume-download <model-id> --local-dir ./models/<model-dir>

这里有两个占位符：

  • <model-id>：远程模型 ID，例如某个组织下的模型名称
  • <model-dir>：本地保存目录，建议和模型版本对应

下载后检查文件：

ls -lh ./models/<model-dir>

通常至少要看到配置文件、tokenizer 文件和权重文件。如果目录里只有部分文件，启动时可能会报 tokenizer、config 或 weight 读取错误。

启动基础推理服务

单卡启动模板：

CUDA_VISIBLE_DEVICES=0 vllm serve ./models/<model-dir> \
  --served-model-name <model-name> \
  --host 127.0.0.1 \
  --port 8000 \
  --tensor-parallel-size 1 \
  --dtype auto

参数说明：

  • CUDA_VISIBLE_DEVICES=0：指定使用第 0 张 GPU
  • ./models/<model-dir>：本地模型目录
  • --served-model-name <model-name>：对外暴露的模型名称，客户端请求时使用
  • --host 127.0.0.1：只允许本机访问，适合调试阶段
  • --port 8000：服务端口
  • --tensor-parallel-size 1：单卡部署
  • --dtype auto：让 vLLM 根据模型和硬件自动选择精度

如果明确知道硬件支持 bf16，也可以指定：

--dtype bfloat16

调试阶段建议先用 127.0.0.1。确认服务稳定后，再根据访问范围决定是否改成 0.0.0.0。

多卡部署模板

多卡推理时，选择参与服务的 GPU，并设置 tensor parallel 数量：

CUDA_VISIBLE_DEVICES=0,1 vllm serve ./models/<model-dir> \
  --served-model-name <model-name> \
  --host 127.0.0.1 \
  --port 8000 \
  --tensor-parallel-size 2 \
  --dtype auto

注意两点：

  • CUDA_VISIBLE_DEVICES 里有几张卡，--tensor-parallel-size 通常就设置为几
  • 多卡不是为了“自动提高所有任务速度”，它主要解决大模型装不下或吞吐需求更高的问题

如果模型单卡能稳定运行，先单卡跑通，再扩展多卡。

验证 OpenAI 兼容接口

vLLM 启动后，可以先看模型列表：

curl http://127.0.0.1:8000/v1/models

再测试 Chat Completions：

curl http://127.0.0.1:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<model-name>",
    "messages": [
      {"role": "user", "content": "用一句话说明 vLLM 的作用"}
    ],
    "temperature": 0.7
  }'

如果请求报模型不存在，优先检查 /v1/models 返回的 ID，并确保请求里的 "model" 字段和它一致。

Python 调用示例：

from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8000/v1",
    api_key="EMPTY",
)

resp = client.chat.completions.create(
    model="<model-name>",
    messages=[
        {"role": "user", "content": "用一句话说明 vLLM 的作用"}
    ],
    temperature=0.7,
)

print(resp.choices[0].message.content)

本地无鉴权时，api_key 可以填占位值。如果服务端配置了 API Key，客户端要同步修改。

常用性能参数

基础服务跑通后，再考虑调性能。常见参数如下：

vllm serve ./models/<model-dir> \
  --served-model-name <model-name> \
  --host 127.0.0.1 \
  --port 8000 \
  --tensor-parallel-size 1 \
  --dtype auto \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90

参数含义：

  • --max-model-len：限制最大上下文长度，越大越占显存
  • --gpu-memory-utilization：vLLM 可使用的 GPU 显存比例
  • --served-model-name：建议固定，方便客户端和配置文件解耦
  • --dtype：不确定时先用 auto，明确硬件能力后再指定

调参顺序建议：

  1. 先用默认参数启动成功
  2. 再调整上下文长度
  3. 再调整显存利用率
  4. 最后做并发和吞吐压测

不要在第一次启动时堆太多参数。服务起不来时，变量越少越容易定位。

开启工具调用

如果要让模型支持 function calling / tool calling，需要同时满足三个条件：

  • 模型本身支持工具调用
  • vLLM 版本支持对应 tool parser
  • 请求中的 tools Schema 写得足够清晰

通用启动模板：

vllm serve ./models/<model-dir> \
  --served-model-name <model-name> \
  --host 127.0.0.1 \
  --port 8000 \
  --tensor-parallel-size 1 \
  --dtype auto \
  --enable-auto-tool-choice \
  --tool-call-parser <tool-parser>

这里的 <tool-parser> 不能随便填，需要根据模型类型和 vLLM 文档选择。常见取值可能包括 hermes、mistral、llama3_json、qwen3_xml 等，具体以当前 vLLM 版本支持列表为准。

如果只是普通问答、摘要、分类、信息抽取，不需要开启工具调用。工具调用主要用于 Agent、自动化编排、查询外部系统等场景。

服务访问控制

调试完成后，如果要给其他机器访问，需要把监听地址改成：

--host 0.0.0.0

但这只解决“能访问”的问题，不解决“谁能访问”的问题。建议至少做一层访问控制：

  • 只在内网开放端口
  • 使用防火墙限制来源 IP
  • 通过 Nginx / Caddy 做反向代理
  • 配置 API Key
  • 给外部访问加 HTTPS

vLLM 支持通过参数设置 API Key：

vllm serve ./models/<model-dir> \
  --served-model-name <model-name> \
  --host 0.0.0.0 \
  --port 8000 \
  --api-key <api-key>

客户端调用时带上：

curl http://<server-ip>:8000/v1/models \
  -H "Authorization: Bearer <api-key>"

模型服务不要直接暴露到公网裸奔。即使只是内测，也应该限制来源 IP 或加鉴权。

后台运行和日志

临时后台运行可以用 nohup：

mkdir -p ~/ai-runtime/logs

nohup vllm serve ./models/<model-dir> \
  --served-model-name <model-name> \
  --host 127.0.0.1 \
  --port 8000 \
  --tensor-parallel-size 1 \
  --dtype auto \
  > ~/ai-runtime/logs/vllm.log 2>&1 &

查看日志：

tail -f ~/ai-runtime/logs/vllm.log

查看进程：

ps aux | grep "vllm serve"

停止服务：

pkill -f "vllm serve"

如果是长期服务，建议使用 systemd、Docker、Kubernetes 或其他进程管理工具。nohup 适合测试，不适合严肃生产环境。

systemd 托管示例

单机长期运行可以写一个 systemd service：

[Unit]
Description=vLLM OpenAI Compatible Server
After=network.target

[Service]
Type=simple
WorkingDirectory=/home/<user>/ai-runtime
Environment="CUDA_VISIBLE_DEVICES=0"
ExecStart=/home/<user>/ai-runtime/vllm_env/bin/vllm serve /home/<user>/ai-runtime/models/<model-dir> --served-model-name <model-name> --host 127.0.0.1 --port 8000 --tensor-parallel-size 1 --dtype auto
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target

保存为：

/etc/systemd/system/vllm.service

启动并设置开机自启：

sudo systemctl daemon-reload
sudo systemctl enable --now vllm
sudo systemctl status vllm

查看日志：

journalctl -u vllm -f

systemd 的好处是进程异常退出后可以自动拉起，也更方便统一查看状态和日志。

部署总结

vLLM 的部署流程可以拆成四层：

层级 核心内容 关注点
底层环境 GPU、驱动、CUDA、PyTorch 先确认硬件和运行时可用，否则服务无法稳定启动
模型资产 模型文件、tokenizer、配置文件、本地目录 保证模型目录完整、版本清晰、路径固定
推理服务 vllm serve、OpenAI 兼容接口、性能参数 让模型以 HTTP API 形式稳定提供推理能力
运维接入 日志、鉴权、反向代理、进程托管、监控 让服务可追踪、可控制、可恢复、可长期运行

真正稳定的本地模型服务，不只是“命令能跑起来”，而是要做到模型名固定、接口可验证、日志可追踪、访问可控制、进程可恢复。这样上层应用接入时，vLLM 才能从临时测试工具变成可靠的推理基础设施。
